ProvostXInference — Consumer Contract

Audience: developers of consumer services (ProvostXLLM, tools, tests). This is the stability promise of the caller-facing surface: what you may touch, what is guaranteed, and what is closed. Anything not listed here is internal and may change without notice.

1. The only entry point

using ProvostXInference.Engines;        // builder, factory, ops views, helper facades
using ProvostXInference.Models;         // config records, EngineStats, EngineTelemetry

var engine = InferenceEngineBuilder.Gguf(modelPath)
    .WithGpuLayers(99)
    .Build();                           // validated EngineRequest, fail-closed
engine.Initialize();
var ops = engine.Gguf;                  // typed view; wrong kind => EngineKindMismatchException

You reference exactly two namespaces: ProvostXInference.Engines and ProvostXInference.Models. Everything else (Implementation, Interop, SafeHandles, Logging, Abstractions) is a closed black box.

2. Engine object lifecycle contract

StepGuarantee
Builder.* → Build()Request validated fail-closed; bad paths/kinds/environments throw typed exceptions before any native work
Initialize()Engine loads; failure leaves the engine unloaded and disposable — no partial state leaks
engine.Gguf / .Decision / .EncoderTyped views over ONE graph; views wrap, never duplicate
Dispose()Teardown in fixed order (pool → context → model); safe to call twice; safe after failed load

3. What IGgufEngineOps guarantees

  • Model/context graph: chat template, tokenize/detokenize, sampling knobs, live

context rebuild (RebuildContext() — old pool is disposed, state is not preserved), KV copy/clear, checkpoints (export/import byte-exact), rewind, shift.

  • Backend probe: Backend reports the TRUTH — active specialist, effective/requested

GPU layers, reduced flag. It never reports CPU for an active accelerator.

  • Stats & telemetry (ABI v9):
  • GetExecutorStats(executor) / GetConversationStats(conv) — per-lane counters

(prompt tokens, decode steps, committed tokens, spec drafted/accepted). Snapshot copy-out; rejected drafts derive as drafted − accepted.

  • GetEngineTelemetry() — model-wide snapshot for THIS engine instance:

EngineTelemetry(PromptTokens, DecodeSteps, CommittedTokens, SpecDrafted, SpecAccepted, Errors, ContextsAlive). Pull-based and per-engine — derive rates between two snapshots in the caller; the engine keeps no rate state.

  • Speculation: capability self-report (SpeculativeCapabilities — supported-types

list, not booleans), validate/enable/disable. Unwired capability ⇒ typed NOT_SUPPORTED naming the boundary. Never a silent plain-generation fallback.

  • Grammar: CreateGrammar (GBNF) / CreateGrammarFromJsonSchema. Every sampled

token passed a grammar check (tiered rejection sampling) — output always conforms.

4. Per-engine audit trail (ABI v9)

Set on the builder via ModelConfig:

SettingMeaning
AuditPath (null/empty = off)JSON-lines audit file for THIS engine instance only
AuditIncludePromptsalso record prompt token counts (never prompt text)

Guarantees:

  • Per-engine isolation: two engines in one process write two independent files and

keep two independent telemetry streams. Nothing is shared (test-pinned).

  • Events: model_loaded, model_freed, context_created, context_freed,

spec_enabled, spec_disabled, kv_cleared, kv_shifted — each {"ts", "seq", "event", "detail"?}, monotonic seq, flushed per line (survives hard kill).

  • Content policy: prompt TEXT is never recorded. Audit logs are not a content sink.
  • Zero cost when off: unconfigured engines execute one branch per commit and

nothing else — no counters, no I/O.

  • Best-effort by design: audit is observability, never a correctness dependency;

an unusable path logs a warning and disables the sink (load still succeeds).

5. Process-wide debug logging vs per-engine audit

  • EngineLogging.SetLogFile/Enable/SetLevel routes the native DEBUG stream

(llama.cpp/ggml/Metal + pvx internal logs). This is process-wide by nature — one specialist module owns the log state. Use it for diagnostics.

  • Use AuditPath for per-engine operation trails. The two are independent channels.

6. Error contract

Every failure is a typed exception carrying an error code, message, and a named boundary (e.g. spec-engine/mtp-wiring, json-schema/parse, kv/rewind):

ExceptionWhen
InferenceExceptionany native-side failure (load, decode, capability, marshaled refusals)
InvalidEngineRequestExceptionbuilder request failed validation
EngineKindMismatchExceptionwrong ops view for the engine kind
PrefillStallUnrecoveredExceptionstall watchdog exhausted its recovery ladder

Refusals are always typed and named — never empty messages, never silent fallbacks, never process aborts on supported paths.

7. Stability rules

  • ABI handshake: the native library version must match the binding; mismatch refuses

to load. Struct layouts are size-pinned by tests.

  • Append-only ABI: new fields are appended; a zeroed struct reproduces previous

behavior bit-for-bit. Consumers compiled against an older surface keep working.

  • No silent behavior changes: every capability boundary refuses typed instead of

degrading. If a feature reports supported, it is verified by tests.

  • Config validation is fail-closed: invalid configs are rejected at build time,

never clamped silently.

8. What is NOT in the contract

  • Anything under Implementation, Interop, SafeHandles, Logging, Abstractions
  • Internal counters not surfaced through the stats/telemetry records
  • Native C API details (the flat pvx_* surface) — consumers go through the facade
  • Prompt text handling inside audit trails (explicitly excluded by policy)

9. Version history

ABIConsumer-visible change

ProvostXInference — Capability & Integration Guide

What It Is

A C/C++ inference engine that links llama.cpp directly and exposes a flat C API for P/Invoke from C#. Replaces LLamaSharp entirely. No wrapper, no managed/native split — we own the entire inference path.

Current State (2026-09-25)

  • 14/14 tests passing on macOS Metal (Apple Silicon, desktop-class)
  • Library size: 11.3MB (statically links llama.cpp + ggml + mtmd)
  • llama.cpp: latest master (e351231c4)
  • Build: cmake with Metal/CPU/CUDA/Vulkan backend flags

Capabilities

Model Management

  • pvx_load_model — load GGUF model with GPU layers, threads, flash attention, KV cache type
  • pvx_free_model — free model
  • pvx_load_mmproj — load vision projector (mmproj GGUF) → mtmd context
  • pvx_free_mmproj — free vision projector

Context

  • pvx_create_context — create llama_context with n_ctx, n_batch, n_seq_max, pooling type
  • pvx_free_context — free context
  • pvx_context_size / pvx_context_seq_max — query context params

Tokenization

  • pvx_tokenize — text → tokens (with add_bos, parse_special flags)
  • pvx_detokenize — tokens → text (with remove_special flag)
  • pvx_token_to_piece — single token → string
  • pvx_token_is_eos — check if token is end-of-generation

Standard Executor (non-batched, one session per context)

  • pvx_executor_create / pvx_executor_free
  • pvx_executor_prompt — tokenize + queue text tokens
  • pvx_executor_prompt_tokens — queue raw tokens
  • pvx_executor_infer — decode pending tokens (one batch)
  • pvx_executor_sample — sample one token (full pipeline: temp, top_k, top_p, min_p, repeat_penalty, presence_penalty)
  • pvx_executor_token_count — current KV token count
  • pvx_executor_rewind — remove last N tokens from KV
  • pvx_executor_reset — clear entire KV (in-place, no context recreation)

Conversation Pool (batched inference)

  • pvx_pool_create — pre-allocate SeqMax conversations (each owns a permanent seq_id)
  • pvx_pool_lease / pvx_pool_return — lease/return conversations (thread-safe)
  • pvx_pool_available / pvx_pool_size — query pool state
  • Key fix: No executor.Create() ever called on request threads → no seq-id leak, no thread-safety crash

Batched Inference

  • pvx_conversation_prompt / pvx_conversation_prompt_tokens — queue tokens per conversation
  • pvx_infer — ONE decode for ALL conversations with pending tokens (true multi-seq batching)
  • pvx_conversation_sample — sample from a conversation's last token
  • pvx_conversation_token_count — per-conversation token count
  • pvx_conversation_rewind / pvx_conversation_reset — per-conversation KV manipulation

Full Sampling Pipeline

  • Temperature scaling
  • Top-k filtering
  • Top-p (nucleus) sampling
  • Min-p filtering
  • Repeat penalty (with configurable window)
  • Presence penalty
  • EOS detection
  • Logits are copied before modification — no corruption of shared internal state

Embeddings

  • pvx_get_embeddings — text → normalized embedding vector
  • Pooling modes: MEAN, CLS, LAST (configurable per context)
  • L2 normalization
  • pvx_embedding_dim — query embedding dimensions

Vision / MTMD

  • pvx_load_mmproj — load mmproj file → mtmd_context
  • pvx_conversation_prompt_with_images — full pipeline:
  1. Decode image bytes (PNG/JPEG) via mtmd_helper_bitmap_init_from_buf
  2. Tokenize prompt + images into chunks via mtmd_tokenize
  3. Text chunks → queue as pending tokens
  4. Image chunks → encode via mtmd_encode_chunk → get float embeddings
  5. Flush pending text tokens (causal decode)
  6. Set non-causal attention → decode image embeddings via embd batch
  7. Restore causal attention
  • pvx_mtmd_marker / pvx_mtmd_marker_static — get the media marker string
  • pvx_mtmd_needs_non_causal — check if model requires non-causal for images
  • pvx_set_causal_attn — per-call causal attention control

Granular KV Cache Manipulation (impossible via LLamaSharp)

  • pvx_conversation_shift_left / pvx_executor_shift_left — sliding window context: remove oldest N tokens, keep recent ones, continue generating without reset. RoPE positions stay correct via separate n_kv_pos tracking.
  • pvx_kv_copy — copy KV from one seq_id to another (state backup without blob serialization)
  • pvx_kv_clear_seq — clear one seq_id's KV without affecting other conversations
  • pvx_set_causal_attn — toggle causal/non-causal attention per-call

State Save/Restore

  • pvx_state_save — snapshot KV to backup seq_id (via llama_memory_seq_cp)
  • pvx_state_restore — restore from backup seq_id
  • pvx_conversation_save / pvx_conversation_restore — per-conversation state
  • Key improvement: No blob serialization, no managed/native split, one atomic operation

Anti-Prompt Detection

  • pvx_check_anti_prompts — check if generated text contains any anti-prompt string

Thread Safety

  • Internal std::mutex infer_mtx on every context serializes ALL native llama.cpp calls
  • Pool has its own mutex for lease/return
  • C# layer handles per-session SemaphoreSlim gates and cycle coordination

What Needs Careful Handling at the C# Layer

1. Vision Processing (Single, Non-Batchable)

The constraint: Image embeddings require non-causal attention (llama_set_causal_attn(ctx, false)). This is a context-wide flag — it affects ALL conversations on that context, not just the one with the image.

What this means for the C# layer:

  • pvx_conversation_prompt_with_images must be called inside the cycle gate (the _cycleGate SemaphoreSlim in BatchInferenceCoordinator)
  • No other conversation can be decoding on the same context while image embeddings are being processed
  • The C++ layer handles the causal/non-causal toggle internally, but the C# layer must ensure exclusive access during the call

Flow:

C# acquires _cycleGate
  → C# calls pvx_conversation_prompt_with_images(conv, mmproj, text, images)
    → C++ flushes text tokens (causal decode)
    → C++ sets non-causal
    → C++ encodes image (CLIP)
    → C++ decodes image embeddings (non-causal)
    → C++ restores causal
  → C# releases _cycleGate
→ Other conversations can now batch normally

Cannot batch multiple conversations' image decodes in one llama_batch because:

  • Text tokens need causal attention
  • Image embeddings need non-causal
  • You can't mix them in one llama_decode call
  • Multiple images COULD be batched (both non-causal), but the CLIP encoding is the bottleneck and mtmd_batch_encode already handles that

2. Shift Left (Sliding Window) — Position Tracking

The constraint: After shift_left(n), the logical token count (n_tokens) decreases but the absolute KV position (n_kv_pos) stays the same. RoPE positions in the remaining KV entries are absolute and must not be reindexed.

What the C# layer must track:

  • n_tokens (logical) — for headroom checks, overflow detection, max_tokens clamping
  • The C++ layer handles n_kv_pos internally — C# never needs to know it
  • After shift_left, the C# layer must re-evaluate headroom: headroom = context_size - n_tokens - safety_margin
  • The C# layer should call shift_left BEFORE the context is full, not after — e.g., when n_tokens > context_size * 0.8, shift left by 10-20% of context size

When to use shift_left vs reset:

  • shift_left: Conversation is long but still relevant. Remove oldest tokens, keep recent context. No re-prompt needed.
  • reset: Conversation is done or corrupted. Clear everything. Must re-prefill.

3. Repeat Penalty in Batch Mode

The constraint: pvx_conversation_sample does NOT apply repeat penalty in batch mode (passes empty recent_tokens). The C++ layer doesn't track per-conversation token history for batch conversations.

What the C# layer must do:

  • Track recent generated tokens per BatchSession in C# (already done via _exactTokenCount and the session's prompt history)
  • If repeat penalty is needed in batch mode, either:
  • Option A: Pass recent tokens from C# to a new pvx_conversation_sample_with_history function (TODO if needed)
  • Option B: Apply repeat penalty at the C# level by post-processing the sampled token (not ideal — can't modify logits after sampling)
  • Option C: Accept no repeat penalty in batch mode (current approach — acceptable for most use cases)

4. Pool Exhaustion

The constraint: The pool has exactly SeqMax conversations. If all are leased and a new request comes in, pvx_pool_lease returns PVX_ERR_NO_SLOT.

What the C# layer must do:

  • Set SeqMax = max_sessions in the config (already done)
  • When PVX_ERR_NO_SLOT is returned, either:
  • Queue the request and retry when a conversation is returned (preferred)
  • Return HTTP 503 (service unavailable) to the client
  • Do NOT create new conversations on the fly — that would exhaust seq_ids (the original bug)

5. State Save/Restore with n_seq_max == 1

The constraint: pvx_state_save copies KV to backup seq_id 1. If n_seq_max == 1, there's no backup seq_id.

What the C# layer must do:

  • For the standard executor (non-batched), set seq_max >= 2 so state save/restore works
  • For batch mode, seq_max = max_sessions (always >= 2), so this is a non-issue
  • If n_seq_max == 1 and state restore is called, the C++ layer returns OK with n_tokens = 0 — the C# layer must re-prompt the conversation

6. Thread Safety Model

The C++ layer guarantees:

  • infer_mtx serializes all native llama.cpp calls within a context
  • Pool mutex serializes lease/return

The C# layer must guarantee:

  • Per-session SemaphoreSlim(1,1) request gate — only one request per session at a time
  • BatchInferenceCoordinator._cycleGate — serializes the drain+infer cycle
  • Vision prompt calls are made from the cycle coordinator thread (under the cycle gate)
  • No concurrent calls to pvx_conversation_prompt_with_images and pvx_infer on the same context

7. Error Recovery

On decode failure (PVX_DECODE_FAILED):

  • The C++ layer does NOT modify n_tokens or n_kv_pos on failure
  • The C# layer should:
  • Log the error
  • Call pvx_conversation_reset to clear the KV (safe — just llama_memory_seq_rm)
  • Re-prompt the conversation from scratch
  • Or call pvx_conversation_rewind to try removing the last prompt

On pool exhaustion (PVX_ERR_NO_SLOT):

  • Queue the request, don't crash
  • Return 503 to the client with a Retry-After header

On model load failure (PVX_ERR_LOAD_FAILED):

  • Check pvx_last_error for the native error message
  • Common causes: wrong path, corrupted GGUF, insufficient VRAM for requested GPU layers

Backend Safety Layer

Automatic detection, probing, and fallback for all GPU backends. No hardcoded assumptions — everything is verified at runtime.

Backend Probe (pvx_probe_backend)

  • After context creation, does a minimal 1-token decode to verify the GPU backend works
  • If it fails → caller retries with fewer GPU layers (pvx_create_context_safe)
  • Detects: Metal, CUDA, Vulkan, CPU via ggml_backend_dev list

Progressive GPU Layer Reduction (pvx_create_context_safe)

  • Try requested_gpu_layers → if fail, try N/2 → N/4 → ... → 0 (CPU)
  • Finds the working threshold automatically — no manual tuning

Vulkan Stale KV Fix (pvx_kv_flush)

  • After llama_memory_seq_rm (pool return), Vulkan may leave stale K/V data in freed cells (#26744)
  • pvx_kv_flush does a no-op decode + clear to flush stale state
  • Automatically called in pvx_pool_return when pvx_backend_needs_kv_flush() returns true
  • On safe backends (Metal/CUDA/CPU), this is skipped (no-op)

Known Issues Addressed

Vulkan:

  • vk::DeviceLostError on long contexts (#19955) → probe catches this
  • FA + quantized V cache = garbled output (#26195) → quantized_kv_safe defaults to false
  • Stale K/V in freed cells (#26744) → pvx_kv_flush after pool return
  • FA + GQA packing + multi-token crash (#26358) → multi_seq_safe flag
  • Batch 512 garbage on some models (#27237) → min_batch_size = 1024
  • load-mode auto OOM (#27360) → progressive layer reduction

Metal:

  • Command buffer failures (1a5631b) → handled gracefully since March 2026 (we have this)
  • Mixed quantized KV when FA unavailable (#21450) → Metal dequantizes internally (70aff25)

CUDA:

  • OOM without warning → progressive layer reduction + probe
  • MoE + FA + partial offload illegal memory access (#26609) → probe detects, can disable FA
  • mmproj VRAM not in auto-fit (#19980) → manual VRAM guard

VRAM Guard (pvx_vram_available)

  • Pre-operation VRAM check (platform-specific implementation TODO)
  • Currently relies on probe + progressive reduction as safety net
  • TODO: Metal (mach_vm_statistics), CUDA (cudaMemGetInfo), Vulkan (vkGetPhysicalDeviceMemoryProperties)

ProvostXInference — Configuration Reference

Summary: ProvostXInference (PVX) is a C/C++ inference library with C# bindings, wrapping llama.cpp. The product code reads zero environment variables — all configuration is passed programmatically via C API structs by the embedding application (e.g., the ProvostX LLM server). Test/benchmark code reads three PVX_* env vars for model paths.

Product Code: Environment Variables

None. A grep of src/*.cpp and csharp/**/*.cs (excluding tests) for getenv / GetEnvironmentVariable returned zero matches. All PVX behavior is controlled by programmatic parameters set by the caller. This was confirmed by audit on 2026-09-26 and remains true as of 2026-09-27.

ProvostXInference — API Glossary

Every public type a consumer can touch, one purpose paragraph each, with the members that matter. Types are listed by layer; the consumer-facing set is deliberately small.

Engines layer (the consumer surface)

InferenceEngineBuilder (static)

Entry point for every consumer. InferenceEngineBuilder.Gguf(path) / .Decision(path) / .Encoder(path) starts a typed request builder; With* methods add parameters; Build() returns a validated EngineRequest. Fail-closed: invalid combinations throw InvalidEngineRequestException before any native work.

InferenceEngineFactory

Constructs IInferenceEngine from a validated request. The default instance needs no configuration (parameterless).

IInferenceEngine (interface)

One loaded-or-unloaded engine object. Initialize() loads it (failure leaves it unloaded and disposable); Gguf / Decision / Encoder return typed ops views; Dispose() tears down in the fixed order pool → context → model.

IGgufEngineOps (interface, via GgufEngineOps)

The GGUF lane view: chat template, tokenize/detokenize, sampling, RebuildContext(), KV copy/clear, checkpoints, rewind/shift, speculation (ValidateSpeculation/EnableSpeculation/DisableSpeculation + ActiveSpeculation), vision encoder load, TTS session create, rerank, LoRA/cvec, Backend probe, GetExecutorStats / GetConversationStats (per-lane EngineStats), GetEngineTelemetry() (model-wide EngineTelemetry), CreateExecutor(), Pool (lazy IConversationPool).

IDecisionEngineOps / IEncoderEngineOps

Decision lane (ONNX judge session) and encoder lane (vision embedding route). Wrong-kind access throws EngineKindMismatchException.

EngineLogging (static facade)

Process-wide native DEBUG stream: SetLogFile(path) (native file sink), Enable(handler) (managed (level, tag, message) callback), SetLevel(0..3, 99). Distinct from the per-engine audit trail (see ModelConfig.AuditPath).

EngineMaintenance (static facade)

File-level engine-bound maintenance without a loaded engine: GGUF EOG/special-token metadata repair.

StallWatchdogOps (static facade)

Sole construction seam for the stall-safe prefill helpers (IPrefillStallDetector, IStallRecoveryLadder, IChunkWallClock).

Abstractions layer (implemented by the native wrappers)

IStandardExecutor

Single-session generation: Prompt(text), PromptTokens(...) (feed-back during generation), Infer() → InferResult, Sample(SamplingConfig) → token, GenerateSpeculative(...), SaveState()/RestoreState(), GetStats(), EnableSpeculation(SpeculativeConfig), PromptWithAudio(...).

IConversation / IConversationPool

Pooled batched lane. Pool: Lease() / return-by-dispose, AvailableCount. Conversation: prompt/sample/grammar (SampleWithGrammar), SaveState()/RestoreState, ExportCheckpoint()/ImportCheckpoint() (byte-exact blobs), Rewind, Reset, GetStats(), SpeculationStats().

IInferenceContext

Per-model decode context: Tokenize/Detokenize/TokenToPiece/IsEos, CreatePool(), CreateExecutor(), KV ops (KvCopy, KvClearSeq), ContextSize, SeqMax.

IInferenceModel

ProvostXInference — FAQ

Real questions from development and integration. Answers are contracts, not marketing.

1. Why not just use LLamaSharp?

LLamaSharp wraps llama.cpp but owns the seams we need to control: batching discipline, KV lifecycle, backend safety, and error typing. We link llama.cpp directly behind our own flat C API so every one of those surfaces is explicit, fail-closed, and test-pinned. The C# layer is strict OOP (one type per file, constructor injection, no statics in product code) — that is a deliberate architectural stance, not style.

2. What happens if the native library version doesn't match the C# binding?

The engine refuses to load. The ABI version is handshake-checked at engine open (PVX_ABI_VERSION vs ExpectedAbiVersion); a mismatch is a fail-closed error, never a best-effort attempt. Struct layouts are size-pinned by tests (PvxAbiSizeTests) so a drift cannot pass silently.

3. Does one process support multiple engines with different models?

Yes — that is a first-class scenario. Each engine instance owns its model, contexts, pools, and telemetry. Two engines write two independent audit files (per-engine audit, ABI v9) and expose two independent GetEngineTelemetry() streams. Nothing is shared except the process-wide DEBUG log stream (EngineLogging), which is a single native log sink by design.

4. Does the audit trail record prompt text?

No — by policy. The audit trail records lifecycle and operation events (model/context lifecycle, spec enable/disable, destructive KV ops) and optionally prompt token COUNTS (AuditIncludePrompts). Prompt text is never written: audit logs must not become a content sink. If you need content, that belongs in your service layer.

5. What does the audit feature cost when I don't configure it?

One branch per commit. Every counter bump and every file write is gated behind audit.enabled; an unconfigured engine executes no counters and no I/O. The feature is dead when not actively set up.

6. A capability reports "supported" but I get a NOT_SUPPORTED exception — why?

You are likely outside a documented lane boundary. Speculation, for example, self-reports capability per MODEL, but some modes are sequential-executor-lane only (the batched/pool conversation lane refuses typed). Every refusal names its boundary (e.g. spec-engine/mtp-wiring, spec-engine/session). The refusal is the contract: the engine never silently falls back to plain generation.

7. Which specialist backend is actually running?

Ask the engine: ops.Backend reports the active specialist, effective vs requested GPU layers, and whether the load was reduced. The probe never misreports an active accelerator as CPU (a historic bug, fixed and pinned by tests). On macOS the metal specialist is the default; Linux/Windows default to cuda → vulkan → cpu in order of availability.

8. How do I get throughput numbers (tokens/second)?

Telemetry is pull-based and stateless: take two GetEngineTelemetry() snapshots around your workload and derive rates in your code (DecodeSteps or CommittedTokens divided by elapsed time). The native side deliberately keeps no rate state — snapshots stay cheap and allocation-free.

9. Can I resume a conversation after a process restart?

Yes — ExportCheckpoint() produces a byte blob (cells + K/V rows) that ImportCheckpoint() restores on a fresh engine, with token counts matching exactly. Verified across dense and hybrid architectures up to the largest test models.

10. Why are model files not in the repository, and why do live tests "skip"?

Models are gigabyte-scale artifacts; the repo ships none (and no native binaries — CI builds every platform slice). Live test lanes discover models via PVX_SMALL_*_PATH env vars or repo-relative fixture locations; when a fixture is absent the lane skips with a named reason instead of failing. The suite is fully green with zero fixtures present (hermetic mode).

11. Is Windows / Linux really supported, or just macOS?

All three build and test in CI (specialist matrix: osx-arm64 metal, win-arm64 cpu, win-x64/linux-x64 cuda+vulkan, plus a full Windows MSVC lane). The real-model journey tier has been verified live on ARM64 Linux and Windows lab VMs. CUDA/Vulkan specialists are CI-built but their real-model verification awaits a GPU host with models — that is stated openly in the backlog, not hidden.

12. What does "fail-closed" mean in practice?

A failure or an unknown state produces a typed error that names what happened and where — it never produces a guessed result. Examples: unknown engine id → refusal listing known specialists; grammar with an unsupported JSON-schema keyword → NOT_SUPPORTED naming the keyword; rewind on a hybrid architecture → REWIND_UNSUPPORTED. We consider a silent wrong answer worse than a loud refusal.
