## Notable failures (exact evidence) — 1 & 2 FIXED 2026-10-18 am, re-verified live

### 1. FIXED — Backend probe misreported Metal as CPU (all GGUF models, default AND explicit `metal` specialist)
- **Evidence:** `backend=CPU probePassed=True gpuLayers eff/req=0/0 reduced=False activeSpecialist=(platform-default)` — identical with `WithGpuLayers(99)` and with explicit `WithEngineId("metal")`. Metal is demonstrably active (embedded metal lib loads; `MTL0` compute buffers allocated; `splits=2` graphs), so this is a misreport, not a CPU-only run.
- **Root cause (code-level):** `src/pvx_backend.cpp` `detect_backend()` greps device names for `"Metal"`, but the vendored ggml names the metal device `GGML_METAL_NAME="MTL"` → `"MTL0"` (see `llama.cpp/ggml/src/ggml-metal/ggml-metal.cpp:15`). `strstr("MTL0","Metal")` never matches → every probe fell through to `PVX_BACKEND_CPU`.
- **Second defect in the same slice:** `original_gpu_layers`/`effective_gpu_layers`/`gpu_layers_reduced` were only written by `pvx_create_context_safe()`, which the C# facade path never uses (it calls per-handle `pvx_create_context` directly), so `BackendInfo` gpu-layer visibility was structurally `0/0` for every facade-created engine.
- **Fix:** detection now skips CPU-class devices and matches the stable vendor-tag device ids (`MTL`/`Metal`, `CUDA`, `Vulkan`); an unrecognized accelerator reports its raw ggml device name (`PVX_BACKEND_GPU_OTHER`) instead of lying "CPU". gpu-layer fields are computed by `pvx_backend_fill_profile()` — called from **`pvx_create_context`** (every facade path) and re-run by `pvx_probe_backend` (requested = model's load-time config; effective = min(requested, n_layer+1), 0 on a CPU verdict).
- **Re-verification (large-memory host, `results-verify.txt` + `flash-probe.final.log`):** `RESULT|…/backend-probe-gpu99|PASS|gpuLayers req=99 → backend=Metal probePassed=True eff/req=29/99 reduced=True` (Llama-3B); identical PASS on Qwen3.5-4B (33/99), Qwen3.6-35B (41/99), Flash-Next (49/99). The in-lane `backend-probe` row flipped too: `backend=Metal probePassed=True gpuLayers eff/req=29/-1 reduced=False`. C# `IGgufEngineOps.Backend` reports the truth through the facade.

### 2. FIXED — `pvx_get_embeddings` SEGFAULTED on generative models with MEAN pooling (dense AND hybrid)
- **Evidence:** `IInferenceModel.GetEmbeddings` with a MEAN-pooling context on Llama-3.2-3B (dense) and Qwen3.5-4B (hybrid) → process dies with SIGSEGV (rc=139), reproducible both when pooling is set at load and via `RebuildContext`; lldb: `EXC_BAD_ACCESS (code=1, address=0x10)`, faulting instruction `ldr x8, [x0, #0x10]` (null-object deref) immediately after the embeddings forward completes (`sched_reserve` printed, graph ran). `RebuildContext(Mean)` + dispose WITHOUT calling GetEmbeddings = PASS (no crash) — the fault is inside the native embeddings read path, not teardown. Encoder-arch embeddings (MiniLM) PASS, so the crash is specific to generative (causal) models + pooling.
- **Contract angle:** a pooling request on a causal model should be a typed error (fail-closed), never a segv. All four gguf-all runs ended rc=139 at this row before the row was split into an isolated subprocess test.
- **Root cause:** the embeddings path called `llama_encode` FIRST and fell back to `llama_decode` on error. `llama_encode` on a decoder-only model builds an ENCODER graph on a causal arch and dies with the observed `EXC_BAD_ACCESS (address=0x10)` right after `sched_reserve` (the graph path the model does not define). MiniLM survived because it takes the encode path for the right reason.
- **Fix:** encode-vs-decode is now routed by the model's own architecture (`llama_model_has_encoder/has_decoder`; typed NOT_SUPPORTED if a model exposes neither). Extraction fails CLOSED (typed error) when no embedding source produces data.
- **Re-verification (large-memory host, `results-verify.txt` / `results-verify3.txt`):** pre-fix repro: `embed-isolate L3B load rc=139`, `embed-isolate Q35 load rc=139`. Post-fix: `RESULT|Llama-3.2-3B/embed-isolate-load|PASS|mean-pooling embeddings dim=3072 L2=1.00 sim=0.819 > disim=0.548` (load AND rebuild); Qwen3.5-4B `dim=2560 … sim=0.723 > disim=0.476`; Qwen3.6-35B `dim=2048 … sim=0.784 > disim=0.568`; MiniLM unchanged (dim=384).
- **Flash-Next (honest boundary, NOT a silent pass):** the merged Q5_K_M file reports `n_embd_out=10240` vs `n_embd=2560` (4-way multi-token output head). llama.cpp's internal MEAN extraction would read 10240 floats from a 2560-wide pooled tensor and its upstream bounds assert ABORTED the process (observed rc=134 on the first verify round). Now a typed fail-closed refusal BEFORE any decode: `InferenceException[code=7]: NOT_SUPPORTED: embeddings: model's output head (n_embd_out=10240) differs from its hidden state (n_embd=2560) - merged multi-token output head cannot be pooled honestly (boundary: embeddings/pooling)` — both at-load and after RebuildContext, rc=0, deterministic dispose (first verify round also exposed a HARNESS lifecycle bug: the undisposed engine on the exception path raced finalizers at exit and tripped the known metal teardown assert — scratch harness fixed to dispose + emit a TYPED verdict; native contract unchanged).

### 3. FIXED (message plumbing) — MTP wiring boundary (expected refusal, now with a named reason)
- **Evidence (all models):** `EnableSpeculation(Mtp)` → `InferenceException[code=7]: NOT_SUPPORTED: PVX_SPEC_MTP_AUTO not wired in this build: MTP drafting requires LLAMA_CONTEXT_TYPE_MTP context plumbing + nextn hidden-state extraction this specialist does not construct yet; the mtp capability reports model-level presence honestly (boundary: spec-engine/mtp-wiring)`. `ActiveSpeculation` stays null after the failed enable; `GenerateSpeculative` without a session → typed `NOT_SUPPORTED: no spec session on this executor (boundary: spec-engine/session)`. No model on disk reports the `mtp` capability bit (the Q5_K_M merged Flash-Next GGUF carries no nextn tensors; the Q8 MTP sidecar exists on disk but has no load path through this API).
- Minor (FIXED): `ValidateSpeculation(Mtp)` on non-mtp models used to throw code 7 with an **empty message string** (`NOT_SUPPORTED:  `). Root cause was twofold: the native `pvx_model_spec_validate` set NO reason string, and the C# layer passed a MODEL handle to `pvx_last_error` (a CONTEXT-handle function — wrong struct layout). Fix (ABI v5): new `pvx_model_last_error(model)` export + native validate writes model-scoped reasons + C# `ThrowIfModelError` retrieves them. Re-verified: `Validate(Mtp)=typed: InferenceException[code=7]: NOT_SUPPORTED: model has no MTP capability (no nextn tensors in the GGUF; boundary: spec-engine/capability)` (the local unit test now also asserts a non-empty reason).
